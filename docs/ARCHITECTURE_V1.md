# معماری نسخه ۱ — Agent Editor

- وضعیت: سند طراحی / هنوز پیاده‌سازی نشده
- نوع محصول: ابزار خصوصی، محلی و تک‌کاربره
- هدف نسخه ۱: ساخت یک هسته قابل اتکا برای تعریف، اجرای کنترل‌شده و بررسی Agentها

## ۱. تعریف محصول

Agent Editor یک محیط مهندسی برای چرخه عمر Agent است: تعریف و پیکربندی، اتصال مدل، تخصیص مهارت و ابزار، اجرای وظیفه، مشاهده روند اجرا، ارزیابی خروجی و اصلاح نسخه.

این پروژه برای استفاده اختصاصی ساخته می‌شود. ثبت‌نام عمومی، چندمستاجری، صورتحساب، فروش Agent، بازار عمومی و زیرساخت SaaS خارج از محدوده هستند.

## ۲. اصول معماری

1. **Local-first:** داده‌ها، تنظیمات، تاریخچه و حافظه به‌صورت پیش‌فرض در فضای محلی نگهداری شوند.
2. **Single-user:** در V1 سیستم حساب کاربری عمومی یا نقش‌های چندکاربره ندارد.
3. **Provider-agnostic:** منطق اصلی نباید به یک API یا SDK خاص وابسته باشد.
4. **Modular monolith:** در شروع یک برنامه با مرزهای ماژولی روشن؛ نه مجموعه‌ای از microserviceها.
5. **Explicit permissions:** هر ابزار مجوز مشخص دارد؛ دسترسی با افزودن Skill به‌صورت پنهانی گسترش پیدا نمی‌کند.
6. **Human approval:** عملیات حساس، مخرب یا بیرونی قبل از اجرا نیازمند تأیید صریح کاربر است.
7. **Observable execution:** هر اجرا باید قابل ردیابی، لغو، بررسی و ارزیابی باشد.
8. **Mobile-conscious UI:** رابط باید در مرورگر موبایل قابل استفاده باشد و طراحی فنی اجرای محلی روی Android/Termux را مسدود نکند.

## ۴. لایه‌ها و مسئولیت‌ها

### 4.1 Control Center
رابط گرافیکی برای:
- ساخت و ویرایش Agent
- انتخاب پروفایل مدل و ابزارهای مجاز
- مدیریت Skillها و حافظه
- شروع، توقف و بررسی اجرای وظایف
- مشاهده خطاها، رویدادها و نتایج ارزیابی

رابط کاربری نباید مستقیماً SDK مدل یا ابزار سیستم را فراخوانی کند؛ همه درخواست‌ها از API برنامه عبور می‌کنند.

### 4.2 Application Layer
هماهنگ‌کننده عملیات سطح محصول:
- `AgentService`: اعتبارسنجی و ذخیره تعریف Agent
- `RunService`: ایجاد و مدیریت Task Run
- `ApprovalService`: ثبت درخواست و نتیجه تأیید
- `WorkspaceService`: مدیریت فایل‌ها و محدوده پروژه
- `EvaluationService`: اجرای آزمون‌ها و ثبت نتایج

### 4.3 Agent Core
هسته اجرای مستقل از ارائه‌دهنده مدل. چرخه پایه:

1. دریافت Task و Agent Definition
2. ساخت Context با رعایت سیاست حافظه و محدودیت توکن
3. تهیه Plan یا گام بعدی
4. درخواست مدل از Model Gateway
5. اعتبارسنجی پاسخ و تشخیص فراخوانی ابزار
6. بررسی مجوز و گرفتن تأیید در صورت نیاز
7. اجرای ابزار و ثبت نتیجه
8. مشاهده نتیجه و تصمیم برای ادامه یا پایان
9. ثبت خروجی نهایی و ارزیابی

حلقه اجرا باید دارای سقف گام، timeout، سقف مصرف، امکان cancellation و مدیریت خطای مشخص باشد؛ اجرای نامحدود مجاز نیست.

### 4.4 Model Gateway
قرارداد مشترک برای مدل‌ها:
- فهرست Provider Adapterها
- پروفایل مدل و پارامترهای تولید
- تبدیل پیام‌ها و پاسخ‌ها به قالب داخلی
- timeout، retry محدود و خطاهای قابل تشخیص
- ثبت متادیتای مصرف در صورت ارائه‌شدن توسط Provider

هیچ ماژول دامنه‌ای نباید مستقیماً به SDK یک فروشنده وابسته شود. کلیدها فقط از متغیر محیطی یا تنظیمات محلی خارج از Git خوانده شوند.

### 4.5 Tool Registry
هر Tool باید manifest معتبر داشته باشد:
- شناسه و نسخه
- توضیح و کاربرد
- ورودی/خروجی دارای schema
- سطح ریسک و مجوز لازم
- timeout و محدودیت خروجی
- سیاست تأیید
- handler اجرایی

سطوح اولیه مجوز:
- `read`: فقط خواندن داده مجاز
- `write`: تغییر داده در فضای کاری مشخص
- `external`: اثرگذاری روی سرویس یا محیط بیرونی
- `system`: دسترسی سطح سیستم؛ در V1 غیرفعال به‌صورت پیش‌فرض

### 4.6 Skill Manager
Skill یک بسته قابلیت مستند و نسخه‌دار است که می‌تواند شامل دستورالعمل، الگوی گردش‌کار، منابع و ارجاع به ابزارهای مجاز باشد. Skill به‌تنهایی مجوز جدید صادر نمی‌کند. فعال‌سازی Skill باید اثر آن بر ابزارها و دسترسی‌ها را شفاف نشان دهد.

### 4.7 Memory Service
سه نوع داده از هم جدا می‌شوند:
- **Run Context:** اطلاعات موقت یک اجرای خاص
- **Workspace Knowledge:** دانش و فایل‌های متعلق به یک پروژه
- **Durable Memory:** داده‌ای که برای استفاده در اجراهای بعدی نگهداری می‌شود

هر حافظه پایدار باید منبع، زمان ثبت و وضعیت اعتبار داشته باشد. کاربر باید امکان مشاهده، اصلاح و حذف آن را داشته باشد. اطلاعات حساس نباید بدون ضرورت ذخیره شوند.

### 4.8 Evaluation & Observability
- رویدادهای ساخت‌یافته برای هر Run
- وضعیت، زمان شروع/پایان و شناسه هم‌بستگی
- ثبت ورودی و خروجی با حذف یا پوشاندن Secretها
- تست‌های نمونه برای کیفیت و تبعیت از محدودیت‌ها
- گزارش خطا و امکان بازتولید تست با ورودی ثبت‌شده، بدون افشای کلیدها

## ۵. مدل داده مفهومی

### AgentDefinition
- `id`, `name`, `description`
- `system_instructions`
- `model_profile_id`
- `tool_allowlist`
- `skill_refs`
- `memory_policy`
- `execution_limits`
- `version`, `created_at`, `updated_at`

### TaskRun
- `id`, `agent_id`, `agent_version`
- `task_input`, `status`
- `started_at`, `finished_at`
- `step_count`, `resource_usage`
- `final_output`, `error_summary`

وضعیت‌های پایه: `queued`, `running`, `waiting_approval`, `completed`, `failed`, `cancelled`.

### RunEvent
- `id`, `run_id`, `sequence`
- `event_type`, `payload_redacted`, `created_at`

### ToolDefinition / SkillDefinition / MemoryItem
هر کدام شناسه پایدار، نسخه یا نوع، متادیتا و زمان ایجاد/به‌روزرسانی دارند. داده‌های بزرگ فایل‌محور در Workspace نگهداری می‌شوند و فقط metadata آن‌ها در SQLite قرار می‌گیرد.

## ۶. پشته فنی پیشنهادی V1

| بخش | انتخاب پایه | دلیل |
|---|---|---|
| Backend | Python 3.11+ و FastAPI | اکوسیستم مناسب Agent و API ساده |
| Data validation | Pydantic v2 | قراردادهای ورودی/خروجی روشن |
| Persistence | SQLite | نصب و نگهداری ساده، بدون سرویس جداگانه |
| Frontend | React + TypeScript + Vite | رابط ساختاریافته و قابل توسعه |
| UI delivery | Web app با طراحی responsive | اجرا در مرورگر موبایل و دسکتاپ |
| Tests | pytest و تست‌های API | آزمون‌پذیری هسته و مرزهای امنیتی |
| Code quality | Ruff و TypeScript checks | قالب‌بندی و خطایابی ایستا |

این انتخاب‌ها مبنای شروع هستند، نه تعهد تغییرناپذیر. در فاز اسکلت، سازگاری نسخه‌ها و نصب روی محیط واقعی بررسی می‌شود. در V1 از Redis، Celery، Kubernetes و معماری microservice استفاده نمی‌کنیم مگر نیاز عملی ثابت شود.

## ۸. مرزهای امنیتی

- Backend در حالت پیش‌فرض فقط روی `127.0.0.1` bind می‌شود.
- فایل `.env`، پایگاه داده، Workspace و خروجی‌های خصوصی در `.gitignore` قرار می‌گیرند.
- Toolها فقط از طریق Registry و پس از اعتبارسنجی schema اجرا می‌شوند.
- ابزارهای فایل فقط در محدوده Workspace مجازند؛ مسیرها باید در برابر path traversal بررسی شوند.
- اجرای shell و دسترسی عمومی به سیستم در V1 غیرفعال است.
- عملیات `write` و `external` بر اساس ریسک نیازمند تأیید هستند.
- ورودی/خروجی، خطا و trace باید پیش از ذخیره از نظر وجود Secret پالایش شوند.
- برای هر Run محدودیت زمان، تعداد گام، اندازه خروجی و مصرف تعیین می‌شود.

## ۹. محدوده نسخه ۱

### داخل محدوده
- تعریف و نسخه‌بندی Agent
- حداقل یک اتصال مدل از طریق Gateway و قرارداد قابل توسعه Provider
- اجرای Task با وضعیت و رویدادهای قابل مشاهده
- Tool Registry با ابزارهای امن و محدود
- Skillهای قابل مشاهده و نسخه‌دار
- حافظه اولیه و Workspace محلی
- تأیید عملیات حساس
- تست و ارزیابی پایه

### خارج از محدوده شروع
- SaaS، ثبت‌نام عمومی و چندکاربره
- فروشگاه یا Marketplace
- پرداخت و اشتراک
- اجرای خودکار و نامحدود کد دلخواه
- استقرار ابری اجباری
- سیستم توزیع‌شده و microservice
- خودمختاری بدون سقف و بدون تأیید

## ۱۰. معیار پذیرش هسته اولیه

V1 زمانی از مرحله هسته اولیه عبور می‌کند که:
1. برنامه در محیط هدف اجرا شود و سلامت API قابل بررسی باشد.
2. بتوان یک Agent را ایجاد، ذخیره و دوباره بارگذاری کرد.
3. بتوان Task را اجرا و وضعیت آن را مشاهده کرد.
4. هر گام و خطا به Run ID مشخص متصل باشد.
5. ابزار بدون مجوز قابل اجرا نباشد.
6. عملیات نیازمند تأیید تا قبل از تصمیم کاربر متوقف بماند.
7. Run با محدودیت زمانی/گامی پایان یابد و قابل لغو باشد.
8. تست‌ها رفتار عادی و مرزهای امنیتی را پوشش دهند.
